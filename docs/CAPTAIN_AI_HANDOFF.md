### Входы и точная математика

1. Для каждого кандидата: f1–f5, нормализованный item embedding128, missing flag и category embedding8. Int8 векторы переводятся в float32 **до** арифметики. Индекс-1 не индексировать; unknown category0, словарь только выбранный train. Embedding_idx относится к конкретному split, а не глобально к item_id.
2. События истории newest-first. Берутся первые 32 позиции, затем исключаются отсутствующие и нулевые векторы. Это порядок событий, **не 32 дня**. Типы событий анонимные, не называть конкретный код «поиск» или «покупка» без расшифровки.
3. User token: user128 + средний recent32 вектор 128 + признак отсутствия пригодной истории. Среднее берётся по нормализованным event vectors, но повторно в единичный вектор token не нормализуется.
4. Дополнительный скаляр 1: cosine предоставленного user vector и кандидата.
5. Дополнительный скаляр 2: посчитать cosine кандидата с каждым пригодным событием recent32, взять **три наибольших и усреднить**. При менее трёх использовать имеющиеся; при пустой истории 0. Три события выбираются отдельно для каждого кандидата. Это среднее cosine, не cosine с усреднёнными top3 векторами.
6. У кандидата остаются ещё два нулевых скалярных слота для совместимости с измеренными весами. Ранги, новая категория и novelty weights **не включать**. В helper signals идут три числа [user_cos, recent_cos, top3_recent_cos]; выбранная модель использует первое и третье. Второе полезно лишь для совпадающего контроля.
7. После scalar slots и category embedding проекция 146→64; user проекция 257→64;4 головы,2 encoder layers, dropout0.1;93353 параметра. Позиции кандидатов не добавлять. В baseline нет позиций кандидатов, attention обрабатывает множество.

Это **не DIN** и не трансформер последовательности истории: top3 — рассчитанный вручную признак. Не подменять модель другой архитектурой при переносе устройства.

## Как адаптировать окружение под NVIDIA

- Python3.11; ознакомься с baseline/pyproject.toml и uv.lock (PyTorch2.10.0). CUDA-enabled сборка и драйвер должны быть совместимы. Проверь torch.cuda.is_available(), версию Torch и имя GPU.
- Если установлена CPU-only сборка, согласуй большой пакет с капитаном и сверь установку с официальной документацией PyTorch. Не угадывай CUDA version и не обновляй Torch молча. При необходимости используй отдельное GPU-окружение; baseline/lock не менять.
- Не переносить Mac .venv. Не считать, что torch.load автоматически перенесёт старые MPS tensors на CUDA: грузить checkpoint сначала через map_location=cpu, затем переносить модель на cuda.
- В своём цикле переносить на cuda features/category/users/padding/history/signals/targets; маски тоже должны быть на корректном устройстве. Исключать padding из BCE и attention. Optimizer создаётся для параметров модели на нужном устройстве.
- Не вызывать torch.mps.* на NVIDIA. mps_memory.py — только Mac. Фиксированный padding может быть полезен, но CUDA memory измерять собственными API, с synchronize до/после замеров. Записывать max_memory_allocated/reserved и host RAM. Не выключать защитные лимиты памяти.
- В progress.py используется Unix resource: на Windows адаптируй **свой** сбор RAM/прогресса или измеряй доступным Windows способом. Не импортировать Mac-specific helper вслепую и не считать его portable launcher.
- Не включать AMP/TF32, другие потери/optimizer/scheduler под видом технического переноса. Если меняешь batch из-за памяти, явно записать это: batch16/32 может менять обучение относительно подтверждённого 64.
- На NVIDIA/Windows эта реализация автором не запускалась. Твоя обязанность — сначала синтетические/малые реальные проверки и memory profile, потом большой прогон. Готовый протокол не означает, что 8GiB гарантированно хватит при любых настройках.

## Что должен делать твой код запуска

Подготовь свой интерфейс с четырьмя режимами: profile, train, evaluate, predict. Команды именуй в своей ветке; в этом пакете намеренно нет нового CUDA runner. Не ищи удалённые train_b02.py, run_b02_final.py и FULL_CPU.md.

### Profile и оценка времени

После разрешения на GPU-окно: несколько прогревочных и достаточно измеренных шагов, включая чтение, признаки на CPU, transfer, forward/backward/AdamW и synchronize. Начать batch16, затем проверить 64 при достаточной памяти. Веса профиля не выдавать за обученную модель. Измерять также val/test чтение и запись, не только GPU kernels.

Предложение капитану:

- время train приблизительно число_лент / измеренные_лент_в_секунду × эпохи;
- отдельно добавить inventory/словарь, val каждой эпохи, запись и test;
- дать диапазон с запасом на холодные чтения/другие shards/нагрев ноутбука;
- не использовать короткий первый файл как точное предсказание всех данных;
- по нашей инвентаризации полный train3151208 лент,50k около 1.6%; подтвердить локальный объём;
- прежнее время Mac не является скоростью NVIDIA. Подтверждённые 8 моделей по 10 эпох заняли 144.88 минут с готовыми кэшами. Порционное построение признаков на лету может быть медленнее.

**Перед большим запуском вернись к капитану с измерением, конкретным объёмом и оценкой времени.**

### Частичный train

Начать с 200–1000 целых train-лент и 100 val, одной эпохи, чтобы проверить сам пайплайн. Это не оценка качества. Затем по бюджету капитана выбрать, например,10k/50k/более крупный объём. Для сопоставимого результата текущий протокол —50k,10 эпох, два seed и полная val. На маленьком screen не объявлять победителя архитектур.

Лимит выбирать **до** перемешивания, не обрывать внутри ленты. Детерминированный shuffle shards/строк с seed+epoch уже показан в HistoryFeeds. Словарь категорий строится только по выбранному train. Данные train/val не объединять.

### Полный train

Полный режим требует отдельного явного согласия капитана и явного флага в твоём интерфейсе.0/отсутствие лимита не должно случайно запустить все данные. Не копировать текущую выборку 50k под названием full.

Сканировать исходные Parquet shards последовательно и держать в RAM максимум один shard. Item embeddings int8 memmap; рассчитывать только retained signals на лету или компактно кэшировать именно их после проверки диска. Старый expanded cache потребовал бы~170GB, поэтому он удалён. Нельзя материализовать полный train в списке тензоров/DataFrame. HistoryFeeds можно использовать как основу: with_signals=True, history_mode=recent32, with_labels=True, pad_to300; num_workers0 до реализации корректного шардирования workers.

Проверь полный inventory: количество лент/кандидатов и максимальную длину. В проверенных данных максимум 299, padding300. Более длинную ленту нельзя молча обрезать: увеличить padding согласованно и повторить memory profile. Windows может не иметь madvise; ОС сама управляет страницами memmap. Не путать mapped size с занятой физической RAM.

Обучать BCEWithLogits на реальных кандидатах, игнорируя padding; затем full NDCG на val и выбор лучшего checkpoint. Сохранять config, seed, commit, dirty state/source hashes, data inventory/покрытие, epoch history, время, RAM/VRAM, best weights и val scores. Промежуточные inference weights без optimizer/RNG не являются точным resume; не обещать продолжение траектории с них.

### Evaluate и predict test

Обучение уже считает val каждой эпохи. После сохранения проверить загрузку лучшей модели и совпадение val scores/метрики. Для test не читать labels. Выполнять тот же preprocessing, свой split embedding_idx, словарь из checkpoint и те же pad/masks. Выдавать float32 logits; feed_id/item_id int32.

Писать прогнозы по батчам в временные Parquet-порции, затем атомарно объединять. Не держать весь test/train prediction в RAM. Проверить точное покрытие и уникальность пары feed_id/item_id, конечность/null/dtype по общему reference. Ключи важнее порядка строк. Для val пересчитать общим evaluator NDCG, @10/@30 диагностически. Для test сохранить время/число лент/кандидатов и SHA256; самостоятельно на сайт не отправлять.

На одной фиксированной малой выборке сравнить CPU/CUDA logits, включая padding/missing. Небольшая численная разница допустима; большой разъезд расследовать до полного запуска. Проверить перестановочную согласованность кандидатов и отсутствие использования target/pos в features.
